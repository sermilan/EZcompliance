## 5 概述

Uniform Resource Locator

### 5.1 概述

---

基于区块链的域名注册数据访问协议定义了从注册管理机构查询和检索注册数据的技术规范。本文件定义了一种方法来查找哪个服务器有权回答请求范围的查询。

顶级域名、自治系统号和网络块由IANA授权给互联网注册管理机构，如TLD注册管理机构和区域互联网注册管理机构，这些注册机构发布进一步的授权及维护信息。本文件基于JSON格式定义了新的注册表，以向客户端发布数据查询权限及路径信息，此处命名为引导服务注册表。另一方面，本文件设计基于区块链的存储管理架构，来更好的保证数据的安全性及一致性，部署和实现时应遵循YD/T AAAA-AAAA 第6章中的规范和要求。

客户端可获取引导服务注册表，提取数据，然后与查询数据进行匹配，以找到权威注册数据服务器和适当的查询基准URL。

## 6 RDAP 引导服务注册表的结构

### 6.1 结构定义

RDAP引导服务注册表已作为JSON对象提供，可通过HTTP从IANA指定的位置检索。每个注册表的JSON对象包含一系列成员，这些成员包含关于注册表的元数据，例如版本标识符、注册表发布日期的时间戳和描述。此外，“services”成员以数组的形式包含注册表项本身。数组的每一项都包含一个二级数组，其中包含两个元素，每个元素都是一个三级数组。

Services数组的每个元素都是一个包含两个元素的二级数组，两个元素依次为Entry数组和服务URL数组。

Entry数组包含具有相同的基本RDAP URL集的所有条目。Service URL数组包含Entry数组中对应条目的基本RDAP URL的列表。这两个数组中的元素不会以任何方式排序。

RDAP引导服务注册表的JSON输出格式的示例结构如下所示：

{
    "version": "1.0",
    "publication": "YYYY-MM-DDTHH:MM:SSZ",
    "description": "Some text",
    "services": [
        [
            ["entry1", "entry2", "entry3"]
        ]
        [
            "https://registry.example.com/myrdap",
            "http://registry.example.com/myrdap/
        ]
        ],
        [
            ["entry4"]
        ]
        [
            "http://example.org/
        ]
    ]
}

---

“version”对应于注册表的格式版本，本规范定义了版本“1.0”。

“publication”值的语法符合互联网日期/时间格式，具体规范参见IETF RFC 3339 第5章中的内容。。该值是IANA对注册表的最新更新日期。

可选的 “description” 字符串可以包含关于引导对象内容的注释。

在每个基本RDAP URLs数组中，应该首选传输协议的安全版本。例如，如果基本RDAP URLs数组同时包含HTTPS和HTTP网址，则引导客户端应该首先尝试HTTPS版本。

基本RDAP URL应有一个尾部的“/”字符，其后跟查询的路径段，各路径段定义应遵循YD/T BBBB-BBBB 第6章中的要求。

JSON名称应遵循YD/T DDDD-DDDD第7章及第8章中的格式要求。实现时应忽略任何无法识别的JSON对象属性或值。

在本文件中定义的注册表中用作条目或基本RDAP URLs的国际化域名标签应仅使用符合规范的A-label形式，标签定义参见IETF RFC 5890 第2.3节中的要求。

本文件中定义的注册表中用作条目或基本RDAP URL的所有域名标签应仅用小写表示。

## 7 域名空间的引导服务注册表

此注册表的JSON输出格式包含附加到根的域标签条目，按基本RDAP URL分组，如附录A.1所示。

域名的权威注册数据服务应通过将目标域名与域名空间的引导服务注册表的Entry数组中的域值进行标签式最长匹配来找到的。从右到左对每个标签进行匹配。如果有多个条目都是最长匹配，则应认为这些条目是等效的。匹配的Service URL数组中包含的值应遵循YD/T BBBB-BBBB第6章中有关路径段规范的要求。

例如，附录A.1所示，a.b.example.com的域名查询应与注册表数组之一中的“com”条目相匹配。然后，这个查询的基准URL取自数组的第二个元素，这个元素是对这个条目有效的基准URL数组。客户端从这个数组中选择一个基准URL；在这个例子中，它选择了唯一一个可用的，“https://registry.example.com/myrdap/”。然后应将具体查询路径段追加到基准URL以完成查询，路径段的定义应遵循YD/T BB BB-BBBB 第6章中的要求。完整的查询是“https://registry.example.com/myrdap/domain/a.b.example.com”。

如果a、b、example、com的RDAP域名查询与注册表中的com和example、com条目都匹配，则应选择最长的匹配（example.com条目）。

如果注册表包含com和goodexample.com这样的条目，那么example.com的域名查询只匹配com条目，因为匹配是基于每个标签进行的。

域名空间根目录的条目被指定为“”。

## 8 互联网号码的引导服务注册表

### 8.1 概述

本节讨论IPv4和IPv6地址空间以及自治系统号。

对于IP地址空间，通过将目标地址与相应引导服务注册表中地址空间的数组值进行最长匹配，可找到权威注册数据服务。最长匹配的方式与路由相同：地址应转换为二进制形式，然后对二进制字符串进行比较，以找到最长匹配至指定前缀长度的字符串。数组的第二个元素中包含的值应是基本RDAP URL，基本URL的定义应遵循IETF 7484 第5章中的要求。最长匹配方法允许在针对一个基本URL的匹配时匹配更长的地址前缀，但是并不包括部分匹配。

---

### 8.2 IPv4 地址空间的引导服务注册表

此注册表的JSON输出格式应包含IPv4前缀条目，以无类域间路由格式指定，并按URL分组，如附录A.2所示。

例如，对 “192.0.2.1/25” 的查询匹配附录A.2示例注册表中的 “192.0.0.0/8” 条目和 “192.0.2.0/24” 条目。后者为最长匹配因此被客户端选择。这个查询的基本RDAP URL取自数组的第二个元素，这个元素是一个对这个条目有效的基本URL数组。客户端从此数组中选择一个基本URL；在本例中，它应选择唯一可用的 “http://example.org/”。指定的资源路径段随后被附加到基本URL以完成查询，资源路径段的定义应遵循YD/T BBBBB-BBBB 第6章中的要求。完整的查询为“https://example.org/ip/192.0.2.1/25”。

### 8.3 IPv6 地址空间的引导服务注册表

该注册表的JSON输出格式应包含IPv6前缀条目，使用地址前缀格式的文本表示，按基本RDAP URL分组，如附录A.3所示。

例如 “2001:0200:1000::/48” 的查询匹配附录 A.3 示例注册表中的 “2001:0200::/23” 条目和 “2001:0200:1000::/36” 条目。后者给出最长匹配被客户端选择。然后，该查询的基本 RDAP URL 从数组的第二个元素中获取，该元素是对该条目有效的基本 URL 数组。客户端应从这个数组中选择一个基 URL，在本例中，它选择 “https://example.net/rdaprir2/”，因为它是协议的安全版本。然后应将指定的路径段追加到基本 URL 以完成查询，路径段的定义应遵循 YD/T BBBB-BBBB 第6章中的要求。因此完整的查询是 “https://example.net/rdaprir2/ip/2001:0200:1000::/48”。如果目标注册数据访问服务器没有回答，那么客户端可使用数组中的另一个 URL 前缀。

### 8.4 自治系统编号空间的引导服务注册表

JSON输出格式包含自治系统号范围条目，按基本URL进行分组，如附录A.4所示。条目数组包含由第二个元素中的基本RDAP URL提供的自动编号范围列表。该数组始终包含两个以十进制格式表示的AS号，表示数组两个元素之间的AS号范围。单个AS号表示的范围为两个相同的AS编号。

例如，对编号65411的查询应与附录A.4示例注册表中的64512-65534项匹配。然后，从数组的第二个元素中获取该查询的基本RDAP URL，该元素是对该条目有效的基本RDAP URL数组。客户端应从这个数组中选择一个基本URL，在本例中，它可选择“https://example.net/rdaprir2”。然后应将指定的路径段追加到基本URL以完成查询，路径段的定义应遵循YD/T BBBB-BBBB 第6章中的要求。因此，完整的查询是“https://example.net/rdaprir2/autnum/65411”。如果服务器没有回答，那么客户端可以使用数组中的另一个URL前缀。

## 9 实体

实体(如联系人、注册人或注册服务商)可通过句柄进行查询，句柄定义应遵循YD/T BBBB-BBBB 第6.2.6节中的要求。由于实体没有全局命名空间，本文件没有描述如何为实体找到权威的服务器。然而，有可能的是，如果实体标识符是从先前的查询中接收的，则可通过相同的服务器查询该实体，或者实体标识符本身是可以被查询的完全引用的URL。

## 10 不存在的条目或 RDAP URL 值

注册表可能不包含请求的值。在这些情况下，对于所请求的值，没有已知的服务器，客户端应该向用户提供适当的错误消息。

## 11 部署和实施注意事项

该方法依赖于这样一个事实，即客户端获取注册表，然后在本地找到服务器。客户端不应每次请求都去获取注册表。客户端应该缓存注册表，但使用底层协议信令，如HTTP Expires头字段，来确定何时刷新缓存的注册表。

如果查询数据与客户端缓存注册表中的任何条目都不匹配，则客户端可以实现各种方法，例如：

a）在域名对象的情况下，客户端可首先查询 DNS，以查看各个条目是否已被授权，或者是否由用户键入错误信息。DNS 查询可以获取 TLD 域的 NS 记录。如果 DNS 的回答是否定的，那么就不需要获取注册表的新版本。但是，如果 DNS 回答是肯定的，这可能意味着当前缓存的注册表不再是最新的。然后客户端可获取注册表、解析，然后执行上面指定的常规匹配。此方法可能不适用于所有类型的注册对象。

b) 如果客户端知道聚合器或重定向器及其相关联的基本 URL 的存在，并且信任该服务，则它可向重定向器发送查询，如果重定向器知道客户端没有找到的权威服务器，则会重定向客户端。

一些注册数据管理机构可能会合作共享他们的信息，以实现共同服务，包括相互重定向。

当分配一个新对象时（例如一个新的AS范围、一个新的TLD或一个新的IP地址范围）不能保证这个新对象将在相应的引导注册表中有一个条目，因为这个新条目的服务器设置可能会在以后注册并生效。因此，客户端应知道即使分配了一个对象，如TLD、IP地址范围或AS范围，也不能保证在相应的引导注册表中存在该条目。

## 12 局限性

### 12.1 局限性说明

除了本文件中描述的对象之外,此方法不提供为任何其他对象查找权威服务器的直接方法。特别是,以下对象不是用本文件中描述的方法引导的:

a) 实体，

b) 以下类型的查询：请求中携带的搜索模式中不包括能够匹配注册表中条目的字符串，

c) 名称服务器，

d) 帮助信息。

## 13 正式的定义

### 13.1 说明

本节是注册表的正式定义说明。在RFC 7159中定义了使用基本类型元素（字符串、数字类型、布尔类型、null）的JSON对象和数组的结构。本文件使用这些元素描述注册表的JSON结构。

### 13.2 导入的 JSON 术语

导入的JSON属于如下:

——OBJECT：一个JSON对象，具体定义参见IETF RFC 7159第4节的内容；

——MEMBER：JSON对象的成员，具体定义参见IETF RFC 7159第4节的内容；

——MEMBER-NAME： 成员名称，定义为“string”，具体描述参见IETF RFC 7159第4节中的内容；

---

——MEMBER-VALUE：成员值，定义为“value”，具体描述参见IETF RFC 7159的第4节中的内容；

——ARRAY：数组，具体定义参见IETF RFC 7159第5节的内容；

——ARRAY-VALUE: 数组的元素，具体定义参见IETF RFC 7159第5节的内容；

——STRING：具体描述参见IETF RFC 7159第7节所定义的“string”。

### 13.3 注册表语法

使用上面的JSON结构术语，注册表的语法定义如下:

——rdap-bootstrap-registry：一个包含版本、发布时间、描述（可选）和服务列表成员的JSON对象；

——version：成员名为“version”，成员值为字符串的成员；

——publication：成员名称为“publication”，成员值为字符串的成员；

——description：成员名称为“description”，成员值为字符串的成员；

——services-list：成员名称为“services”，成员值为一个服务数组（services-array）的成员；

——services-array：一个数组，其中每个数组值都是一个服务；

——service：一个包含两个元素的数组，其中第一个数组值是一个条目列表（entry-list），第二个数组值是一个服务网址列表（service-uri-list）；

——entry-list：一个数组，其中每个数组值都是一个条目（entry）；

——entry：条目，一个字符串；

——service-uri-list：一个数组，其中每个数组值都是一个service-uri；

——service-uri：服务URI，一个字符串。

## 14 安全考虑

通过提供一种引导方法来查找服务器，本文件有助于确保终端用户将从权威来源而不是无效、非法来源获得注册数据。该方法具有与基于区块链的域名注册数据访问协议本身相同的安全属性。通过使用IANA支持的TLS，用于访问注册表的传输可以更加安全。

实现和部署时应遵循YD/T CCCC-CCCC中规定的其他安全注意事项。

“version” 对应于注册表的格式版本，本规范定义了版本 “1.0”。

在每个基本RDAP URLs数组中，应该首选传输协议的安全版本。例如，如果基本RDAP URLs数组同时包含HTTPS和HTTP网址，则引导客户端应该首先尝试HTTPS版本。

基本RDAP URL应有一个尾部的“/”字符，其后跟查询的路径段，各路径段定义应遵循YD/T BBBB-BBBB 第6章中的要求。

在本文件中定义的注册表中用作条目或基本RDAP URLs的国际化域名标签应仅使用符合规范的A-label形式，标签定义参见IETF RFC 5890 第2.3节中的要求。

## 7 域名空间的引导服务注册表

此注册表的JSON输出格式包含附加到根的域标签条目，按基本RDAP URL分组，如附录A.1所示。

域名的权威注册数据服务应通过将目标域名与域名空间的引导服务注册表的Entry数组中的域值进行标签式最长匹配来找到的。从右到左对每个标签进行匹配。如果有多个条目都是最长匹配，则应认为这些条目是等效的。匹配的Service URL数组中包含的值应遵循YD/T BBBB-BBBB第6章中有关路径段规范的要求。

例如，附录A.1所示，a.b.example.com的域名查询应与注册表数组之一中的“com”条目相匹配。然后，这个查询的基准URL取自数组的第二个元素，这个元素是对这个条目有效的基准URL数组。客户端从这个数组中选择一个基准URL；在这个例子中，它选择了唯一一个可用的，“https://registry.example.com/myrdap/”。然后应将具体查询路径段追加到基准URL以完成查询，路径段的定义应遵循YD/T BB BB-BBBB 第6章中的要求。完整的查询是“https://registry.example.com/myrdap/domain/a.b.example.com”。

如果a、b、example、com的RDAP域名查询与注册表中的com和example、com条目都匹配，则应选择最长的匹配（example.com条目）。

如果注册表包含com和goodexample.com这样的条目，那么example.com的域名查询只匹配com条目，因为匹配是基于每个标签进行的。

域名空间根目录的条目被指定为“”。

## 8 互联网号码的引导服务注册表

### 8.1 概述

本节讨论IPv4和IPv6地址空间以及自治系统号。

对于IP地址空间，通过将目标地址与相应引导服务注册表中地址空间的数组值进行最长匹配，可找到权威注册数据服务。最长匹配的方式与路由相同：地址应转换为二进制形式，然后对二进制字符串进行比较，以找到最长匹配至指定前缀长度的字符串。数组的第二个元素中包含的值应是基本RDAP URL，基本URL的定义应遵循IETF 7484 第5章中的要求。最长匹配方法允许在针对一个基本URL的匹配时匹配更长的地址前缀，但是并不包括部分匹配。
