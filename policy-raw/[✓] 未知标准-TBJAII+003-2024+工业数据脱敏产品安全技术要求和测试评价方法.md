3.1

工业数据 Industrial data

## 数据脱敏 Data desensitization

工业企业在研发设计、生产制造、经营管理、运行维护、平台运营等过程中产生和收集的数据。

### 3.2 

对某些敏感信息通过脱敏规则进行数据的变形，实现敏感隐私数据的可靠保护。

## 静态数据脱敏 Static data desensitization

### 3.3 

将数据抽取出生产环境进行变形转换处理。静态脱敏通常会在将生产环境中的敏感数据交付至开发、测试或外发环境的场景中使用，在降低数据敏感程度的同时，最大程度保留原始数据集所具备的内在关联性等特点，并最大程度保留其具备的可挖掘价值。

## 动态数据脱敏 Dynamic data desensitization

### 3.4 

对于外部申请访问的数据进行即时处理并返回脱敏后结果。动态脱敏通常会在对外提供数据查询服务的场景中使用，在降低数据敏感程度的同时，最大程度上降低了需求方获取脱敏后数据的时延，请求实时产生的数据也能即时得到脱敏后结果。

### 3.5 

## 脱敏算法 Desensitization algorithm

---

对数据进行脱敏处理过程中使用特定数据变形的机制。

### 3.6 

脱敏规则 Desensitization rules

对于特定的敏感数据应用一种或多种脱敏算法组合进行脱敏处理。

### 3.7 

脱敏策略 Desensitization strategy

根据特定的业务场景选择相对应的脱敏规则或算法对敏感数据进行脱敏。

### 3.8 

工业数据脱敏产品 Industrial data desensitization products

是指通过采集SCADA、PLC、DCS、ERP等系统的数据，以及工业主机、数据库等软硬件设备的数据，经过数据收集、梳理、清洗、转换等预处理过程，利用敏感数据梳理识别与数据脱敏产品引擎实现对敏感数据的深度分析和脱敏处理的产品。一般通过预设脱敏算法、脱敏规则和脱敏策略，选择脱敏任务执行子模块，实现脱敏产品灵活配置。

## 6 工业数据脱敏技术要求

### 6.1 安全功能要求

#### 6.1.1 工业数据源自动发现

工业数据源自动发现功能要求包括：

a）数据自动发现功能。应支持访问和获取所兼容的数据库当中的数据库定义、表格定义、字段定义、索引定义、约束定义等，支持识别的数据源及数据格式包括：

1）市场主流操作系统，包括 AIX、HPUXLinux、Windows 等；

2）多种类的数据库作为源或目标数据源，包括 Oracle、Microsoft SQLServer、IBM DB2、MySQL、Sybase、Informix、南大通用、Gbase，支持 Hadoop、Teradata、TDH、CDH 等大数据平台；

3）非结构化数据，包括 TXT、CSV、Word、Excel、Oracle dump、XML、html、PDF、DBF、MP3、MP4 等；

4）动态数据流，包括 API 数据（如 Restful）以及消息队列（如 RabbitMO RocketMO、ActiveMO、Kafka、ZeroMO 等）。

b）特定敏感数据类型的自动发现功能。应根据数据自身的特征，包括类型、长度、数据本身的编码特征、校验算法特征、语义特征等等进行数据分析、分类判断，分辨包含但不限于以下种类的数据类型：

1）研发数据域（研发设计数据、开发测试数据等）；

2）生产数据域（控制信息、工况状态、工艺参数、系统日志等）；

---

3）运维数据域（物流数据、产品售后服务数据等）；

4）管理数据域（系统设备资产信息、客户与产品信息、产品供应链数据、业务统计数据等）；

5）外部数据域（与其他主体共享的数据等）。

#### 6.1.2 敏感工业数据识别与工业数据脱敏

敏感工业数据识别与工业数据脱敏功能应支持敏感工业数据的梳理识别、脱敏计划管理、脱敏任务执行、脱敏结果输出，具体要求包括：

## a）敏感数据梳理识别

1）敏感数据发现规则：应支持用户自定义敏感数据发现规则；

2）敏感数据识别：应支持根据用户定义的脱敏规则，自动匹配脱敏算法，识别敏感数据；

3）数据分类分级：应支持按照工业数据分类分级相关国家、行业标准对敏感数据进行分类分级，支持对分类分级结果进行人工复核。

## b）脱敏计划管理

1）脱敏算法管理：应支持采用随机映射、固定映射、遮盖填充等信息脱敏算法进行脱敏计划设置。信息脱敏算法及示例见附录B；

2）脱敏规则管理：应支持灵活采用一种或多种脱敏算法组合设置脱敏规则；

3）脱敏策略管理：应支持在生产环境和非生产环境(开发、测试、预发布、灰度等)执行相应的脱敏方法，并应具备明确定义敏感数据使用场景的能力。

## c）脱敏任务执行

1）任务调度：应支持自动并行数据抽取功能；

2）关联性保持：应支持工作时间暂停和继续数据抽取作业功能，并且在定义的工作时间结束后抽取作业能够在暂停点继续运行，以减少对生产系统的影响，支持系统定义和用户自定义的工作日和假日定义。

## d）脱敏结果输出

1）数据库接口输出：应能够提供各种访问接口供外部应用调用，包括不限于：脱敏策略配置相关接口、脱敏任务执行管理相关接口、脱敏任务监控相关接口等；

2）文件接口输出：应具备对接口调用方进行鉴权的能力，鉴权内容方式包括：Token 验证、调用方 IP 地址验证、调用方应用编码验证等；

3）其他接口输出：应支持 Web Service 接口、Restful API 接口等开放接口形式。

#### 6.1.3 静态数据脱敏产品技术要求

静态数据脱敏产品应具备以下功能：

a）脱敏任务配置：应对脱敏任务进行相关配置，确定脱敏数据源与目标数据源；配置脱敏数据项与相关脱敏策略；配置脱敏数据模式，全量还是增量；脱敏任务执行方式配置，可以是手动、定时或周期执行等；

b）脱敏任务的管理：应支持脱敏任务查询、修改、删除；

c）脱敏任务执行：应能够按照配置正确执行，能够启动、停止等；

d）任务监控：应对于已发布的脱敏任务提供统一的监控功能；

e）效果评估：应支持脱敏前后数据的效果评估，包含但不限于：算法有效性、规则匹配度、关联性检查等。

#### 6.1.4 动态数据脱敏产品技术要求

---

动态数据脱敏产品应具备以下功能：

a）动态脱敏服务：通过动态脱敏模块供外部调用实时返回脱敏后数据。可通过修改现有数据访问协议实现实时的数据脱敏，如通过SQL改写实现数据库脱敏；

b）脱敏规则继承：在敏感数据发生迁移、复制后，新产生的敏感数据以及对于原始敏感数据的引用会继承原敏感数据的脱敏规则；

c）接口管控能力：应能管控数据源的多种访问方式，包括针对JDBC接口的数据脱敏，对于API、客户端等会对外暴露数据的接口等；

d）最小影响能力：动态数据脱敏过程对生产环境应用完全透明、无感知。

### 6.2 应用场景要求

应用场景应支持开发和测试、生产和运维、共享和分析等应用场景，具体要求包括：

a）开发测试使用业务系统中的真实数据时，需要通过脱敏手段保证敏感数据不被泄露，在此场景中静态脱敏的具体要求如下：

1）应支持主流关系型数据库、大数据平台、格式化文本文件、Oracle dump 文件；

2）自动抽取生产中心数据、自动发现敏感数据，并自动匹配脱敏算法、规则、策略，实现脱敏过程自动化；

3）应保证脱敏前后主外键一致、业务关联一致、有依赖字段的敏感信息脱敏一致、多次脱敏结果一致等，整体保证脱敏前后一致性，保持数据间的逻辑关系；

4）应根据实际业务需求提供脱敏数据，宜通过数据子集、黑名单、白名单等方式控制数据脱敏范；

5）宜支持对生产数据全量和增量的方式脱敏，支持设置脱敏作业的调度周期，并支持对作业过程进行监控，支持脱敏前后的数据比对。

b）生产和运维：运维人员在运维的工作中直接连接生产数据库，能够查询数据库中的敏感数据，存在敏感数据泄露风险，需要根据用户权限不同，对查询的敏感数据进行脱敏处理，在此场景中动态脱敏的具体要求如下：

1）应能够获取登录数据库的用户信息；

2）应根据用户的业务需求不同，为用户设定不同的脱敏策略；

3）应能够记录脱敏操作的日志，并提供日志审计；

4）应支持查询数据库表、视图、同义词等对象脱敏。

c）共享和分析：数据共享分析需要对特定敏感数据进行处理，保留部分敏感数据，从而实现数据共享或者部分数据分发给第三方或上游组织，在此场景中静态脱敏的具体要求如下：

1）应支持预设敏感对象库，根据实际需求自定义敏感对象，设定敏感对象后按照权限进行数据脱敏：

2）应支持对脱敏源中的脏数据（不符合敏感对象业务特征的数据）进行变形处理，避免隐性敏感数据泄露；

3）应保证主外键一致、业务关联一致、有依赖字段的敏感信息脱敏一致、多次脱敏结果一致等。整体保证脱敏前后一致性，保持数据间的逻辑关系；

4）应支持不同数据分析场景匹配不同的数据脱敏算法，宜具有数据分段脱敏的能力，从而保证脱敏后的数据进行安全的数据分析。

### 6.3 安全管理要求

工业数据脱敏产品应具备以下基本要求：

a）应支持对用户身份的合法性进行验证，同时利用控制策略进行选用和管理工作；

---

b）应支持按角色进行分级权限管理，针对操作员按照脱敏算法、脱敏规则、脱敏任务等不同粒度进行权限控制；

c）应支持对系统操作进行日志审计，包括数据源操作、脱敏规则操作、脱敏算法操作、脱敏任务执行操作、运维管理操作等。

## 工业数据脱敏产品的应用

当前工业数据脱敏产品主要包括静态脱敏、动态数据脱敏产品两大类。由于两者使用场景不同，关键技术有所差异。静态脱敏典型应用场景包括开发测试、数据共享、科学研究。动态脱敏典型应用场景包括业务脱敏、运维脱敏、数据交换脱敏。

### A.1 静态脱敏

静态数据脱敏产品一般应用在非生产环境或脱离原业务系统使用，如业务系统中包含工艺参数、设计数据等这些相对敏感信息，但是由于开发测试需要使用这些真实的数据，因为就需要通过脱敏手段保证敏感数据不被泄露。

#### A.1.1 开发测试

a）开发测试场景中，如工业领域业务系统中含有工艺参数、设计数据等敏感信息，由于开发测试需要使用这些真实数据，因此需要通过脱敏手段保证敏感数据不被泄露。

1）数据库类型多，系统体系架构复杂，跨系统和跨平台测试数据难以获取；

2）生产环境和开发测试环境还是存在一定的差异，彼此不相通，所以对脱敏后数据与业务的一致性有严格的要求；

3）要求具备多种脱敏算法，对不同的字段数据有多种脱敏算法。

4）工业系统日新增数据量较大，无法定期对全量数据进行脱敏，要求数据脱敏产品系统具备增量脱敏能力。

## b) 产品应具备的关键功能

1）支持主流关系型数据库、大数据平台、格式化文本文件、Oracle dump 文件；支持敏感数据自动发现、自动抽取生产中心数据、并自动匹配脱敏算法，实现脱敏过程自动化。

2）保证主外键一致、业务关联一致、有依赖字段的敏感信息脱敏一致、多次脱敏结果保持一致等，整体保证脱敏前后一致性，保持数据间的逻辑关系；支持将源数据库对象自动同步到目标库，包括表结构、主键、索引、约束、视图、触发器、存储过程等。

3）支持对于 Oracle dmp 文件进行直接解析，并进行脱敏处理。

4）数据脱敏产品根据实际业务需求提供脱敏数据，可通过数据子集、黑名单、白名单等方式控制数据脱敏产品范围。

---

5）支持对生产数据全量和增量的方式脱敏，可设置脱敏的作业的调度周期，并对作业过程进行监控，支持脱敏前后的数据线比对功能。

6）格式化脱敏：根据数据的格式对数据进行切分，以保证数据的原始特征。

7）依赖脱敏：根据原有数据计算关系，来设置依赖脱敏策略，使脱敏后的数据能保持原有计算关系。

##### A.1.2. 数据共享应用场景

a） 数据共享场景在一些特定需求下，需要对特定敏感数据进行处理，保留部分敏感数据，交付给企业内部的其他部门或者外部企业。

1）数据共享场景中，特定需求下需要保留部分敏感数据字段，但对其他隐私数据可以进行遮蔽、仿真等操作。

2）作为数据提供方，需要提供溯源机制，当发生数据泄露的时候，可以确定数据泄露方，便于溯源追责。

## b) 产品应具备的关键功能

1）预设丰富的敏感对象，包括研发设计、开发测试、控制信息、工况状态、工艺参数等，在进行数据脱敏时，将会对设定的敏感对象按照规则进行脱敏，且可根据实际需求自定义敏感对象，完善敏感对象库。

2）对于脱敏源中存在的脏数据（不符合敏感对象业务特征的数据），系统同样会对这部分数据进行变形处理，以避免隐形敏感数据泄露。

3）内置数据水印及溯源功能，用户可自定义水印内容，同时通过算法保证水印内容的抗破坏性，从而保证在数据被分享给第三方后，可通过系统进行溯源及追责。

##### A.1.3. 科学研究应用场景

a) 数据科学研究核心是将对数据进行统计分析，用于科学研究。需要保证数据特征，脱敏后保证科学研究所必须的内容。

1）为保证获取的数据可以满足科学研究，保留数据部分要真实有效。

2）脱敏后的数据需要有分析的价值，数据的业务特征不能丧失。

3）大数据分析平台中包括海量的工艺参数和敏感数据，针对大数据环境进行数据脱敏产品，数据结构复杂，包括结构化、非结构化数据等，脱敏操作复杂。

4）特定场景下需对脱敏数据进行复敏。

## b) 产品应具备的关键功能

---

1）内置丰富的数据脱敏产品算法及数据分段脱敏的能力，可适配不同的数据分析场景，从而在保证数据脱敏产品或降敏的前提下，安全地进行各种数据分析。

2）保证主外键一致、业务关联一致、有依赖字段的敏感信息脱敏一致、多次脱敏结果保持一致等，整体保证脱敏前后一致性，保持数据间的逻辑关系。

3）支持 HDFS、Hive、Impala、ODPS、Teradata、Greenplum、MongoDB、FusionInsight 等大数据敏感源。

4）支持数据脱敏产品复敏，具备复敏权限的用户才能进行此操作，充分保证安全性。

### A.2 动态脱敏

动态脱敏常用在访问敏感数据即时进行脱敏，一般用来解决在生产环境需要根据不同情况对同一敏感数据读取时进行不同级别脱敏的场景，如业务脱敏、运维脱敏、数据交换脱敏等场景。

#### A.2.1 业务脱敏

a) 业务用户访问应用系统时，需明确用户身份的真实性。

b) 不同权限业务用户访问敏感数据时需采取不同级别的脱敏规则。

c) 对于遗留系统（旧系统无法再作升级改造）以及开发时未考虑《网络安全法》中要求的个人隐私保护问题，重新更改代码过于复杂，只能依赖于外部技术实现数据的隐私保护。

d) 产品应具备的关键功能

1）一键式的敏感数据发现功能，盘点梳理数据库里面的敏感资产，并对相关资产进行分类分级，支持 SCHEMA、敏感表、敏感列等不同的数据集合。

2）识别业务系统三层的用户身份，针对不同的身份采用不同的动态脱敏策略，对不同权限的用户可分别返回真实数据、部分遮盖、全部遮盖等脱敏结果。

3）支持基于敏感标签的脱敏访问策略，支持 B/S、C/S 等不同架构的业务系统、支持对字符串类型、数据类型、日期类型数据脱敏产品，通过随机、转换、遮盖方式实现对动态数据的脱敏效果，防止业务敏感数据信息和业务的个人隐私数据泄漏，保护关键资产数据。

4）无需对应用系统进行改造、无需修改数据库及存储数据，即可实现数据动态脱敏。

#### A.2.2 运维脱敏

a) 共享、临时账号滥用现象，导致运维身份不清。

---

b) 特权用户访问敏感数据，行为不受管控。

c) 运维人员涉及到高危操作、误操作等问题，一旦关键数据丢失，数据难以进行恢复。

d) 数据库内部操作无法审计分析，事后无法进行追责溯源。

## e) 产品应具备的关键功能

1）采用多因素认证机制，进行多方位鉴定识别。

2）特权账号访问控制，禁止 DBA、SYSDBA、Schema User、Any 等特权用户访问和操作敏感数据集合。

3）对未授权的运维身份访问敏感数据实现动态脱敏功能。

4）危险性操作防范（如可执行DDL、DML、代码类的高危操作）、敏感操作临时性授权、智能化监控与告警；支持数据库快速恢复能力，在发生误操作、恶意操作造成数据丢失后，几秒之内完成任意规模表格的数据恢复；

5）全面运维审计，记录包括用户名、IP地址、MAC地址、客户端程序名、执行语句的时间、执行的SQL语句、操作的对象等，对其行为进行全程细粒度的审计分析。

#### A.2.3 数据交换

a) 通过API接口方式向特定平台提供数据。

c) 产品应具备的关键功能

b) 需针对用户信息提供不同的脱敏策略。

1）支持根据 API 传过来的用户信息进行识别、支持 API 所属应用系统的身份识别、支持 API 所属的终端信息身份识别、支持对数据库账户信息识别。

2）根据多因素身份识别，对不同API里面的用户访问采用不同的脱敏策略。
